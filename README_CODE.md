## งบแสดงการเปลี่ยนแปลงส่วนของเจ้าของ (ทางเลือก A) — รอบล่าสุด


งบนี้เป็น **ตาราง 2 มิติ** ไม่เหมือนอีกสามงบ (แถว = รายการเคลื่อนไหว,
คอลัมน์ = องค์ประกอบของส่วนของเจ้าของ 10+ คอลัมน์, และซ้ำสองบล็อกปี)
โครงข้อมูลปลายทางมี 4 ช่อง จึงเก็บเฉพาะ **คอลัมน์ยอดรวม** ซึ่งเป็นส่วนที่มีค่าที่สุด

**ผลลัพธ์: ยอดปลายงวดตรงกับงบฐานะการเงิน 6 จาก 9 บริษัท**

3 บริษัทที่ไม่ตรงเป็นเพราะ **คอลัมน์ขวาสุดไม่ใช่ยอดรวม** — IIG จบตารางที่
ส่วนได้เสียที่ไม่มีอำนาจควบคุม ไม่มีคอลัมน์รวมเลย การแก้ต้องอ่านชื่อคอลัมน์
จากหัวตารางที่พาดแนวตั้ง 4 บรรทัด ซึ่งเป็นงานของทางเลือก B

**สิ่งสำคัญ: มันไม่ได้เงียบ** — สมการข้ามงบจับได้เองทั้ง 3 บริษัท

### การตรวจข้ามงบ (ของใหม่ที่ได้จากงบนี้)

```
SE_CLOSING = TOTAL_EQUITY   (ยอดปลายงวด = รวมส่วนของเจ้าของในงบฐานะการเงิน)
CASH_END   = CASH           (เงินสดปลายงวด = เงินสดในงบฐานะการเงิน)
```

เป็นการตรวจที่แข็งแรงที่สุดที่มี เพราะเทียบตัวเลขจากคนละหน้าคนละตาราง
ถ้าอ่านหน้าใดหน้าหนึ่งผิดจะไม่มีทางบังเอิญตรงกัน — ต่างจากสมการภายในงบเดียวกัน
ที่ยังพลาดได้ถ้าดูดมาผิดทั้งตาราง (เคยเกิดกับ GABLE)

**ใช้ได้เฉพาะคอลัมน์งวดปัจจุบัน** เพราะ "งวดก่อน" ของแต่ละงบไม่ใช่วันเดียวกัน
(งบฐานะการเงิน = สิ้นปีก่อน, งบกำไรขาดทุน/กระแสเงินสด = งวดเดียวกันปีก่อน)
ตอนแรกผมไม่ได้แยกตรงนี้ ทำให้สมการล้ม 49 ข้อโดยไม่ใช่ความผิดของตัวสกัด

**ข้อยกเว้นที่รู้แล้ว**: IIG นิยาม "เงินสด" ในงบกระแสเงินสดว่าหักเงินเบิกเกินบัญชีแล้ว
จึงต่างจากงบฐานะการเงิน 23,303,800 โดยตั้งใจ — สมการนี้จะล้มสำหรับ IIG เสมอ

## ทางเลือก B (เก็บทั้งตารางงบเปลี่ยนแปลงส่วนของเจ้าของ) — เริ่มแล้ว ยังไม่จบ

### ทำได้แล้ว: ประกอบชื่อคอลัมน์จากหัวตารางที่พาดแนวตั้ง

`extract_fs.equity_column_names()` — หัวตารางงบนี้พาด 3-4 บรรทัด ชื่อคอลัมน์
เดียวถูกตัดเป็นท่อนๆ วิธีประกอบคือจับกลุ่มคำในแต่ละบรรทัดแล้วผูกกับคอลัมน์ที่
**ขอบขวา**ใกล้ที่สุด (หัวตารางจัดชิดขวาตามคอลัมน์ตัวเลข) แล้วต่อจากบนลงล่าง

ทดสอบแล้วอ่านชื่อได้ถูกต้อง 3 จาก 4 บริษัท เช่น GABLE

```
คอลัมน์ 265  "รวม ส่วนของผู้ถือหุ้นของบริษัทฯ"
คอลัมน์ 287  "ส่วนได้เสียที่ไม่มีอำนาจควบคุมของบริษัทย่อย"
คอลัมน์ 312  "รวม ส่วนของผู้ถือหุ้น"          <- ยอดรวม
```

ยังมีสิ่งเจือปนจากหัวข้อที่ครอบหลายคอลัมน์ (`งบการเงินรวม`, `(หน่วย: พันบาท)`)
ต้องกรองออกตอนแปลงเป็น concept

### แก้แล้ว: คัดหน้างบรวม/งบเฉพาะกิจการจากหัวเรื่อง

`equity_page_side()` อ่านหัวเรื่องของหน้าแทนการเดาจากลำดับ แล้วต่อลำดับแถว
ข้ามหน้าของกลุ่มเดียวกันก่อนตัดบล็อกปี

**ผล: ยอดปลายงวดตรงกับงบฐานะการเงิน 6 → 8 จาก 9 บริษัท**

```
AIS   120,577,940 = 120,577,940   ตรง
```

### SCB วางหน้าปีใหม่ไว้ก่อนปีเก่า

โค้ดเดิมถือว่า "บล็อกสุดท้าย = งวดปัจจุบัน" ซึ่งจริงกับทุกบริษัทยกเว้น SCB
ที่วางหน้า 9 = ปี 2569 และหน้า 10 = ปี 2568 กลับลำดับกัน จึงหยิบยอดปีก่อนมา

แก้โดยเลือกบล็อกจาก **ปี พ.ศ. ที่เขียนในหัวบล็อก** ไม่ใช่ลำดับ

**กับดักซ้อน**: ปีในชื่อแถวถูก `strip_note_ref()` ตัดทิ้ง เพราะมันมองว่าเลข
ท้ายชื่อคือเลขอ้างอิงหมายเหตุประกอบงบ (`หุ้นกู้ 6, 10`) ต้องเก็บปีกลับมา
หลังจับคู่ concept เสร็จ

**กับดักระหว่างทาง**: BBIK ไม่เขียนหัวเรื่องฝั่งงบรวม แต่เขียนฝั่งงบเฉพาะกิจการ
ถ้าเชื่อผลการคัดแบบครึ่งๆ กลุ่มงบรวมจะว่างเปล่าและทิ้งทั้งหน้าไปเงียบๆ
(tech-08 ตกจาก 100% เหลือ 92%) จึงต้องบังคับว่า **ระบุได้ครบทุกหน้าและมีครบ
ทั้งสองฝั่ง** ถึงจะเชื่อ ไม่งั้นถอยไปใช้ลำดับหน้าแบบเดิม

### IIG — คอลัมน์ยอดรวมล้นไปอยู่หน้าถัดไปทั้งคอลัมน์

**ผมเคยสรุปผิดว่า "ตารางของ IIG ไม่มีคอลัมน์ยอดรวม"** ความจริงคือตารางกว้างเกิน
กรอบกระดาษ คอลัมน์สุดท้ายจึงถูกดันไปอยู่หน้าถัดไป **ทั้งคอลัมน์ลอยเดี่ยวๆ**

```
หน้า 8 ของ IIG (ทั้งหน้ามีแค่นี้)
    (หน่วย: บาท)
    รวม
    680,593,011
    ...
    220,811,040
    6              <- เลขหน้า
```

หน้าแบบนี้มีตัวเลขน้อยเกินเกณฑ์ `has_table()` จึงไม่ถูกจัดเป็นงบใดๆ แล้วหายไปเงียบๆ

`equity_spill_values()` จับหน้าแบบนี้แล้วผูกค่ากลับเข้าแถวตามลำดับ
**มีตัวกันสำคัญ: จำนวนค่าต้องเท่าจำนวนแถวพอดี ไม่งั้นไม่ใช้** เพราะถ้าเลื่อนไป
หนึ่งแถวจะได้ตัวเลขที่ดูสมเหตุสมผลแต่ผิดทุกช่อง

กับดักซ้อน: แถวที่ทุกองค์ประกอบเป็น `-` (เช่น `เงินปันผลจ่าย`) เดิมถูกข้าม
ทำให้นับได้ 8 แถวขณะที่คอลัมน์ล้นมี 9 ค่า ต้องนับแถวพวกนี้ด้วยเมื่อมีคอลัมน์ล้น

**ผลสุดท้าย: ยอดปลายงวดตรงกับงบฐานะการเงิน 9/9 บริษัท**

### เจอสาเหตุจริงของ AIS / CPF / IIG ที่ทางเลือก A พลาด (บันทึกไว้)

**ไม่ใช่เรื่องเลือกคอลัมน์ผิด แต่เป็นเรื่องจำนวนหน้า**

```
GABLE MFEC PTT PRG SAT   [รวม, เฉพาะ]              2 หน้า  <- ถูกต้อง
AIS                      [รวม, รวม, ?, ?]          4 หน้า
CPF                      [รวม, รวม, ?]             3 หน้า
SCB                      [รวม, รวม, ?, ?]          4 หน้า
IIG                      [?, ?] แต่ห่างกัน 4 หน้า
```

โค้ดปัจจุบันถือว่า **หน้าแรก = งบรวม ที่เหลือ = งบเฉพาะกิจการ** ซึ่งผิดสำหรับ
AIS/CPF/SCB ที่งบรวมกินสองหน้า (ตารางกว้างเกินหรือแยกบล็อกปีคนละหน้า)
หน้าที่ 2 ของงบรวมจึงถูกอ่านเป็นงบเฉพาะกิจการแล้วทับค่ากันเอง

**วิธีแก้ที่ควรทำก่อนทางเลือก B**: คัดว่าหน้าไหนเป็นงบรวม/เฉพาะกิจการจาก
หัวเรื่องของหน้า ไม่ใช่จากลำดับ แล้วรวมหลายหน้าของกลุ่มเดียวกันเข้าด้วยกัน
งานนี้เล็กกว่าทางเลือก B มากและปิดช่องโหว่ 3 บริษัทได้ทันที

## tech-09 TRUE งบฐานะการเงิน (บริษัทแรกของตระกูล "กลุ่มบริษัทใหญ่" ที่มีเฉลย)

ผล: 224/224 ช่อง = 100% ความครอบคลุม 100% | สมการงบดุลผ่าน 8/8 ทั้ง 4 คอลัมน์

### บั๊กที่เจอ 3 ข้อ

**1. pandas อ่านชื่อบริษัท "TRUE" เป็น boolean `True`**
อาการร้ายมาก: ไม่มี error ใดๆ แต่ ground truth ของ TRUE เทียบกับผลสกัดไม่ติดสักช่อง
วัดได้ 10.3% ทั้งที่ตัวสกัดถูก 100% (ที่เหลือ 10.3% คือช่องว่างที่บังเอิญตรงกัน)
แก้ที่ `core.read_gt` + `evaluate.py` + `crosscheck.py` แปลง company เป็นข้อความเสมอ
บทเรียน: ชื่อบริษัทที่ตรงกับคำสงวนของ CSV (TRUE/FALSE/NA/NULL/NaN) ต้องบังคับชนิดข้อมูล

**2. `unit` ตรวจไม่ออกเมื่อหน่วยเขียนเป็นคำโดดในแถวหัวคอลัมน์**
TRUE และ Thai-Stanley เขียน `หมายเหตุ  พันบาท  พันบาท ...` ไม่ใช่ `(หน่วย: พันบาท)`
ยังไม่ได้แก้ในตัวสกัด ตอนนี้กรอกใน ground truth ด้วยมือ (TRUE=thousand, STANLEY=baht)

**3. `--company X` พร้อม `--pdf-dir <โฟลเดอร์>` ตั้งชื่อบริษัททับทุกไฟล์**
ตั้งใจให้ใช้กับไฟล์เดียว แต่ถ้าชี้ไปที่โฟลเดอร์จะได้ 656 แถวจากทุกบริษัทติดป้ายว่า TRUE
และดูเหมือนตัวสกัดพังยับ ทั้งที่เป็นการเรียกผิด -> ถ้าจะสกัดบริษัทเดียวให้ชี้ไปที่ไฟล์ .pdf โดยตรง

## OCR — วัดผลแล้วว่าแย่ลงแค่ไหน (ไม่ใช่แค่ "ทำได้")

รันบน Kaggle เพราะ sandbox ในเครื่องไม่มีสิทธิ์ root จึงลง tesseract-ocr-tha ไม่ได้

### สถาปัตยกรรม: ไม่แก้ตัวสกัดเดิมสักบรรทัด
    ocr_reader.py   ภาพ -> tesseract (image_to_data) -> ประกอบเป็น text layer
                    ที่รักษาพิกัด x เหมือน pdftotext -layout
    ocr_extract.py  สลับ core.page_text / core.n_pages ให้อ่านจากผล OCR
                    ที่เหลือ (find_columns, parse_line, ตัวอ่าน SE) ใช้ของเดิมหมด

ต้องใช้ image_to_data ไม่ใช่ image_to_string เพราะ image_to_string คืนข้อความล้วน
ที่ทำลายพิกัดไปแล้ว ตัวเลขคนละคอลัมน์จะถูกวางชิดกันจนแยกไม่ออก

### ผลวัด 3 ระดับ — ยิ่งวัดละเอียด ตัวเลขยิ่งต่ำ
    ระดับที่ 1  ตัวเลขปรากฏในหน้าไหม (MFEC)              96.6%
    ระดับที่ 2  ค่าอยู่ถูกช่องไหม (MFEC เทียบ tech-01)     63.1%
    ระดับที่ 3  ใช้ได้จริงกับสแกนจริง (CP ALL / Humanica)  36% / 41%

**ระดับที่ 1 หลอกตา** เพราะนับแค่ว่าข้อความตัวเลขโผล่ที่ไหนสักแห่งในหน้า
ไม่ตรวจว่าไปอยู่ถูกคอลัมน์ถูกแถวไหม ตัวเลขที่อ่านถูกแต่ตกผิดคอลัมน์ยังนับเป็น "ถูก"
พอวัดระดับช่องจริงเหลือ 42.9% ตอนแรก แก้บั๊ก layout แล้วขึ้นมาที่ 63.1%

### ระดับที่ 2 แยกละเอียด (MFEC งบฐานะการเงิน 84 ช่อง — text layer ได้ 100%)
    text layer                      100.0%
    OCR เข้มงวด (หัวเรื่องตรงตัว)    50.0%   ค่าผิด 0 ช่อง
    OCR ผ่อนปรน (หัวเรื่องคล้าย)     63.1%   ค่าผิด 5 ช่อง

**ผ่อนเกณฑ์ = ได้ข้อมูลมากขึ้น แต่ได้ค่าผิดมาด้วย** และค่าผิดตรวจไม่ได้ถ้าไม่มีเฉลย
จึงไม่เลือกแทนผู้ใช้ แต่ติดป้าย page_how ไว้ทุกแถว

### ระดับที่ 3 — ผลจริงกับ PDF สแกน (CP ALL 43 หน้า / Humanica 32 หน้า)
ทั้งคู่ **ไม่ผ่านด่านตัดสินใจ** จึงไม่ถูกรวมเข้า all.csv

| สัญญาณ | CP ALL | Humanica | เกณฑ์ |
|---|---|---|---|
| จับคู่รายการบัญชีได้ | 36% | 41% | >= 50% (text layer ปกติ 60-70%) |
| มาจากหน้าที่มั่นใจ | 81% | 37% | >= 50% |
| งบที่เจอ | BS CF IS SE | BS CF IS | มี BS |
| หน่วยเงิน | thousand | baht | ไม่ใช่ unknown (ต้องใส่ --unit เอง) |
| สมการงบดุล | ผ่าน 0 ผิด 0 ข้าม 32 | - | ผ่าน >= 1 |

**"ผ่าน 0 ผิด 0 ข้าม 32" คือระบบตรวจสอบบอดสนิท** ไม่ใช่ "ไม่เจอปัญหา"
ข้ามทั้งหมดเพราะไม่มี TOTAL_ASSETS / TOTAL_LIABILITIES ให้สมการใช้
เกณฑ์ตอนแรกเขียนว่า "ไม่มีข้อไหนไม่ผ่าน" ซึ่งผลนี้เข้าเงื่อนไขทั้งที่ไม่ได้ตรวจอะไรเลย
-> แก้เป็น "ต้องผ่านอย่างน้อย 1 ข้อ" บทเรียน: เกณฑ์ที่เขียนเป็นเชิงลบล้วนหลอกตัวเองได้

### บั๊กที่เจอระหว่างทำ (42.9% -> 63.1%)
1. char_w คำนวณจากคำไทยด้วย -> สระบน/ล่างไม่กินความกว้างแต่ถูกนับใน len()
   ทำให้ char_w เล็กเกินจริง คอลัมน์เพี้ยนทั้งหน้า
   -> คิดจาก token ที่เป็นตัวเลขล้วนเท่านั้น
2. tesseract หั่นข้อความไทยเป็นชิ้นเล็ก พอใส่ช่องว่างคั่นทุกชิ้น ชื่อรายการยาวขึ้น
   จนล้นไปทับคอลัมน์ตัวเลข -> เชื่อชิ้นที่ห่างน้อยกว่า 0.5 เท่าของ char_w
3. หัวเรื่องอ่านพลาดตัวเดียว หน้าถูกทิ้งทั้งหน้า
   "งบฐานะการเงิน" -> "งง ฐาน ะกาง ร` น"  โครงไม่ตรง page_kind คืน None
   -> เพิ่มชั้นสำรองใน ocr_extract (หัวเรื่องคล้าย >= 0.75 แล้วค่อยดูเนื้อหา)
      **ไม่แตะ fs_core** เพราะตัวนั้นผ่านเฉลย 14 ชุดที่ 100% อยู่แล้ว
4. RecursionError: แทน core.page_kind ด้วย lambda ที่ข้างในเรียก core.page_kind
   -> เก็บอ้างอิงตัวเดิมไว้ตั้งแต่ import (_STRICT_PAGE_KIND)

### ข้อสรุปและสิ่งที่ตัดสินใจไม่ทำ

**tesseract ไม่พอสำหรับ PDF สแกนภาษาไทย** — ปิดเรื่อง OCR ที่ตรงนี้

ไม่ไล่ต่อจาก 63% เพราะที่เหลือไม่ใช่ปัญหา layout แล้ว แต่เป็นความสามารถของ
tesseract เอง (CASH, TOTAL_ASSETS, TOTAL_LIABILITIES ถูกอ่านพลาดทั้งบรรทัด)
และทุกครั้งที่ผ่อนเกณฑ์เพื่อดันตัวเลขขึ้น ค่าผิดจะเพิ่ม ซึ่งสวนทางกับจุดขาย

ถ้าจะทำต่อ **ต้องลงทุนที่ตัว OCR ไม่ใช่ที่ layout** (easyocr / Typhoon OCR ของ
SCB10X ซึ่งทำมาเพื่อเอกสารไทยโดยเฉพาะ / Google Vision) ตอนนี้มีฐานวัดครบแล้ว
เอา OCR ตัวใหม่มาเสียบแทนใน ocr_reader.py แล้ววัดด้วยชุดเดิมได้ทันที
เทียบกับ 63.1% ได้ตรงๆ ไม่ต้องเริ่มใหม่

**สิ่งที่ได้จริงจากงานนี้ ไม่ใช่ "ทำ OCR ได้"**
แต่คือระบบที่บอกได้ว่า OCR เชื่อได้แค่ไหน แยกได้ว่าความผิดพลาดเป็นแบบ
"ข้อมูลหาย" (สมการจับได้) หรือ "ข้อมูลผิด" (จับไม่ได้) และมีด่านตัดสินใจ
ที่ทำให้ข้อมูลคุณภาพต่ำ **ไม่หลุดเข้าระบบ** โดยไม่มีใครรู้

### ที่มาของข้อมูลติดไปกับทุกแถว
    reader    = text / ocr
    page_how  = หัวเรื่อง / หัวเรื่องคล้าย 0.88 / เนื้อหา
