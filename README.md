# Thai Financial Statement Extraction & Validation

สกัดงบการเงินไทยจาก PDF ที่ text layer เพี้ยนทุกไฟล์ **พร้อมระบบที่บอกได้ว่าเมื่อไหร่ตัวเองผิด**

| | |
|---|---|
| ข้อมูล | งบการเงินไตรมาส 1/2569 · 13 บริษัท (SET) · 4 ประเภทงบ |
| ผลสกัด | 1,807 บรรทัด · 251 รายการบัญชี |
| ความแม่นยำ | **100%** เทียบเฉลยที่ตรวจด้วยมือ **2,705 ช่อง** |
| ความครอบคลุม | **100%** — เฉลยทุกแถวถูกนำมาเทียบจริง ไม่มีแถวไหนถูกข้าม |
| ตรวจตัวเอง | 267 สมการผ่าน · ผิด 0 (ไม่ต้องใช้เฉลย) |

> **ทำไมต้องรายงานความครอบคลุมคู่กับความแม่นยำ** — ถ้าเฉลย 8 แถวแต่เทียบจริงแค่ 6
> ตัวเลข "100%" จะสวยเพราะ *ไม่ได้ตรวจ* ไม่ใช่เพราะ *ถูก*
> เคยเกิดจริงกับชุด SCB และแก้แล้ว (ดู `README_CODE.md` ข้อ 19)

## ปัญหา

PDF งบการเงินไทยเกือบทุกไฟล์มี text layer ที่**อ่านออกมาแล้วไม่ตรงกับที่ตาเห็น**

```
ที่ตาเห็น    ลูกหนี้การค้าและลูกหนี้หมุนเวียนอื่น
ที่ dump ได้  ลกู หน้กีารคา้              (IIG)
             เงินฝากธนาคารทีมB ีภาระคาประก   (GABLE)
             องค์ประกอบอืน8 ของส่วนของผู้ถือหุ้น   (BBIK — วรรณยุกต์กลายเป็นเลข 8)
```

สระ วรรณยุกต์ และช่องว่างเพี้ยนไม่เหมือนกันในแต่ละไฟล์ ขึ้นกับโปรแกรมที่ผลิต PDF
การจับคู่ชื่อรายการด้วยข้อความตรงตัวจึงใช้ไม่ได้เลย

**และปัญหาที่ใหญ่กว่านั้น** — ความผิดพลาดของงานประเภทนี้มัก *ไม่* ทำให้โปรแกรม error
แต่ให้ตัวเลขที่หน้าตาสมเหตุสมผลแล้วผิด ซึ่งอันตรายกว่าการพังเสียอีก

## แนวทางแก้

### 1. จับคู่ด้วย "โครงพยัญชนะ" ไม่ใช่ข้อความ

ตัดสระ วรรณยุกต์ ตัวเลข และช่องว่างทิ้ง เหลือแต่พยัญชนะไทย `[ก-ฮ]`

```
"ลูกหนี้การค้า"  ->  ลกหนกรค
"ลกู หน้กีารคา้"  ->  ลกหนกรค     ตรงกัน
```

พยัญชนะแทบไม่เคยเพี้ยน — สิ่งที่เพี้ยนคือสระและวรรณยุกต์ ซึ่งเราตัดทิ้งไปแล้ว

### 2. ตำแหน่งคอลัมน์ตัดสินจากพิกัดตัวอักษร ไม่ใช่การนับ token

ช่องที่งบเขียน `-` ทำให้จำนวน token ไม่คงที่ ถ้านับ token ค่าจะเลื่อนทั้งแถว
ตัวเลขในงบชิดขวาเสมอ จึงใช้ "จุดสิ้นสุดของ token" เทียบกับตำแหน่งคอลัมน์

> ใช้ `pdftotext -layout` เท่านั้น **ห้ามใช้ pdfplumber** — มันแทรกช่องว่างกลางตัวเลข
> (`704,121` -> `7 04,121`) ทำให้ค่าผิดโดยไม่มีสัญญาณเตือน

### 3. ตรวจตัวเองด้วยสมการบัญชี — ไม่ต้องมีเฉลย

งบที่ถูกต้องต้องบวกลบลงตัว

```
สินทรัพย์หมุนเวียน + ไม่หมุนเวียน = สินทรัพย์รวม
หนี้สิน + ส่วนของเจ้าของ          = รวมหนี้สินและส่วนของเจ้าของ
เงินสดต้นงวด + เพิ่ม(ลด)สุทธิ      = เงินสดปลายงวด
ยอดปลายงวดในงบส่วนของเจ้าของ      = ส่วนของเจ้าของในงบฐานะการเงิน   (ข้ามงบ)
```

ใช้ได้กับทุกบริษัทแม้ไม่มีคนมากรอกเฉลย จึงจับได้ว่าค่าไหน "หน้าตาสมเหตุสมผลแต่มาจากตารางผิด"

**267 สมการผ่าน · ผิด 0**

### 4. เฉลยที่กรอกด้วยมือ — เพราะสมการอย่างเดียวไม่พอ

**2,705 ช่องที่คนอ่านจาก PDF แล้วพิมพ์เอง** ไม่ได้เอาผลจากโค้ดมาใส่
(ถ้าทำแบบนั้น ความแม่นยำจะเป็น 100% เสมอและไม่มีความหมายอะไรเลย)

แต่ละแถวติดป้าย `trap` ว่ากำลังทดสอบความยากแบบไหน

| trap | ทดสอบอะไร |
|---|---|
| `parentheses` | วงเล็บ = ค่าติดลบ |
| `thai_digit` | วรรณยุกต์กลายเป็นตัวเลขกลางชื่อ |
| `long_name` | ชื่อยาวถูกตัดขึ้นบรรทัดใหม่ |
| `same_name` | สองแถวชื่อเหมือนกันเป๊ะ แยกได้ด้วยหัวข้อกลุ่มเท่านั้น |
| `note_col` | คอลัมน์เลขอ้างอิงหมายเหตุที่ต้องไม่ถูกอ่านเป็นค่า |

วัดแยกตาม trap เพราะระบบจะพังที่ trap ไม่ใช่ที่บรรทัดปกติ

## ทำไมต้องมีทั้งสมการและเฉลย

**สมการตรวจได้แค่ "ไม่ขัดกันเอง" ไม่ได้แปลว่า "ถูก"**

พิสูจน์ด้วยการทดลอง: จำลองเลื่อนคอลัมน์ทั้งหน้าไป 1 ช่อง

```
สมการตามแถว     ผ่าน 428/428    จับไม่ได้เลย
เฉลย tech-14    จับได้ 11/11 หน้า
```

เพราะเมื่อคอลัมน์เลื่อน ทั้งยอดต้นงวด รายการเคลื่อนไหว และยอดปลายงวดเลื่อนพร้อมกันหมด
สมการก็ยังลงตัวสวยงาม **ทั้งที่ตัวเลขทุกตัวไปอยู่ผิดองค์ประกอบ**

และเรื่องนี้เกิดขึ้นจริง — ตอนที่ตัวสกัดนับคอลัมน์เกินมา 1 ใน 4 หน้า
สมการผ่าน 100% ตลอดเวลาที่บั๊กนั้นอยู่ จับได้เพราะนับคอลัมน์เทียบกับ PDF ด้วยตา

### ทดสอบว่าตัวทดสอบมีพลังจริงไหม

สุ่มเปลี่ยนค่าทีละช่อง 300 ครั้ง แล้วดูว่าระบบตรวจจับได้กี่ครั้ง

```
จับได้ 300/300
```

เฉลยที่ผ่านแต่จับความผิดพลาดไม่ได้ ก็ไม่ต่างอะไรกับไม่มีเฉลย

## OCR — วัดแล้วไม่ผ่าน จึงไม่นำเข้าระบบ

CP ALL และ Humanica เป็น PDF สแกน ไม่มี text layer เลย ต้องใช้ OCR
ผลวัด 3 ระดับ **ยิ่งวัดละเอียด ตัวเลขยิ่งต่ำ**

| ระดับ | วิธีวัด | ผล |
|---|---|---|
| 1 | ตัวเลขปรากฏในหน้าไหม | 96.6% |
| 2 | ค่าอยู่ถูกช่องไหม (เทียบเฉลยที่ text layer ได้ 100%) | **63.1%** |
| 3 | ใช้ได้จริงกับสแกนจริง | **36% / 41%** |

**ระดับที่ 1 หลอกตา** เพราะนับแค่ว่าตัวเลขโผล่ที่ไหนสักแห่ง ไม่ตรวจว่าอยู่ถูกคอลัมน์ถูกแถว

ทั้ง CP ALL และ Humanica **ไม่ผ่านด่านตัดสินใจ จึงไม่ถูกรวมเข้าระบบ**
สิ่งที่บันทึกไว้แทนคือเหตุผลและตัวเลข — ระบบรู้ตัวว่าทำไม่ได้ ดีกว่าปล่อยข้อมูลคุณภาพต่ำเข้ามาเงียบๆ

## โครงสร้างโค้ด

```

extract_fs.py           ตัวสกัดหลัก (งบฐานะการเงิน / กำไรขาดทุน / กระแสเงินสด / ส่วนของเจ้าของ)
se_matrix.py            ตัวอ่านงบส่วนของเจ้าของแบบเต็มตาราง (long format)

evaluate_se_matrix.py   วัดความแม่นยำของตารางส่วนของเจ้าของ + ทดสอบพลังการตรวจจับ
crosscheck.py           ตรวจด้วยสมการ ไม่ต้องมีเฉลย

ocr_reader.py           OCR -> text layer ที่รักษาพิกัด (เพื่อให้ตัวสกัดเดิมใช้ได้)
ocr_extract.py          ต่อผล OCR เข้าตัวสกัดเดิมโดยไม่แก้โค้ดเดิม
dashboard.py            Streamlit — ข้อมูลการเงินคู่กับหลักฐานความน่าเชื่อถือ

account_aliases_v6.csv  พจนานุกรมชื่อรายการบัญชี 511 บรรทัด · 254 concept
tech-*.csv              เฉลยที่กรอกด้วยมือ 14 ชุด
```

## วิธีรัน

```bash
pip install pandas streamlit
sudo apt install poppler-utils          # ต้องมี pdftotext

python run_all.py --pdf-dir ./pdfs      # รันการตรวจทั้งหมดแล้วสรุปให้
streamlit run dashboard.py
```

`run_all.py` รันครบทั้ง 7 ขั้น แล้วสรุปเป็นตารางเดียว ถ้ามีอะไรไม่ผ่านจะขึ้นรายการ
และคืน exit code 1 (ใช้กับ CI ได้)

```
1. selfcheck              unit test 33 ข้อ + ตรวจ alias map ชนกันไหม
2. validate_ground_truth  เฉลยแต่ละชุดสอดคล้องกันเองไหม
3. extract_fs             สกัดทั้ง 4 งบ
4. evaluate x 13          เทียบเฉลย — รายงานทั้งความแม่นยำและความครอบคลุม
5. crosscheck             สมการบัญชี ไม่ต้องใช้เฉลย
6. se_matrix              ตารางงบส่วนของเจ้าของแบบเต็ม + สมการตามแถว
7. evaluate_se_matrix     เทียบตารางนั้นกับเฉลย + ทดสอบพลังตรวจจับ
```

หรือรันทีละขั้นเองก็ได้

```bash
python selfcheck.py
python extract_fs.py --statement all --out all.csv
python evaluate.py   --gt tech-01.csv --extracted all.csv
python crosscheck.py --extracted all.csv
python se_matrix.py  --out se_m.csv
python evaluate_se_matrix.py --gt tech-14_se_matrix_template.csv \
       --extracted se_m.csv --power
```

## บันทึกระหว่างทาง

[`README_CODE.md`](README_CODE.md) บันทึกบั๊กทุกตัวที่เจอ สาเหตุ และเหตุผลที่แก้แบบนั้น
รวมถึง **สิ่งที่ลองแล้วถอยกลับ** ซึ่งมีค่าพอกับสิ่งที่ทำสำเร็จ

ตัวอย่างบั๊กที่ *ไม่* ทำให้โปรแกรม error แต่ให้คำตอบผิด

| บั๊ก | อาการ |
|---|---|
| `NOTES_MARK` พิมพ์โครงพยัญชนะด้วยมือแล้วมีสระค้าง | ตัวกันหน้าหมายเหตุ**ไม่เคยทำงานเลย**ทั้งโปรเจกต์ |
| pandas อ่านชื่อบริษัท `TRUE` เป็น boolean | เทียบกับเฉลยไม่ติดสักช่อง วัดได้ 0% ทั้งที่ตัวสกัดถูก 100% |
| Excel ตัดเลข 12 หลักเหลือ 6 หลักนัยสำคัญ | เฉลยที่กรอกมาผิดเอง โดยไม่มีอะไรเตือน |
| ค่าติดลบในวงเล็บทำให้ตำแหน่งเลื่อน 1 ตัวอักษร | ทั้งแถวหายไปเงียบๆ |

## ข้อจำกัดที่รู้ตัว

- **ไตรมาสเดียว** — ยังไม่มีคอลัมน์ `period` จึงเทียบข้ามไตรมาสไม่ได้
- **PDF สแกนยังใช้ไม่ได้** — วัดแล้ว 36–41% ไม่ผ่านเกณฑ์ (ดูหัวข้อ OCR)
- **เฉลยครอบคลุม 30 จาก 50 ชุด (บริษัท × งบ)** — เลือกแบบแบ่งชั้นตามความยากของ layout
  ไม่ใช่สุ่มทั่วไป งบกระแสเงินสดยังเป็นจุดที่เฉลยบางที่สุด
- **หน่วยเงินของ IIG อ่านไม่ได้** — เอกสารไม่เคยเขียนหน่วยไว้เลย ระบบเลือกเตือนแทนการเดา
